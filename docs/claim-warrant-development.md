# Claim-warrant development: writer × judge

This is a **development** experiment on the completed P5-domain human-audit sample, not a rerun of P5 or a new validation set. It asks whether evidence-bounded rewriting and a clause-aware relation judge improve different parts of the claim pipeline. The original 1,024-request outcomes and 3,181 relation decisions remain unchanged.

## Comparison and estimand

The frame is the exact 200 main audit claims: 160 probability-sampled and 40 enriched. The 20 pilot items are excluded. Each item has the same visible evidence in all four cells. One cached source claim and one generated rewrite are each assessed by the legacy and warrant judges, using the pinned `gpt-4.1-2025-04-14` snapshot. The rewrite is generated **once** per item and reused for both judges; the order of the two judge calls is balanced by a hash of case ID. The cached writer does not call the provider. No human labels, family/arm/condition identities, reviewer rationale, or local paths enter provider payloads.

| Writer | Legacy judge | Warrant judge |
| --- | --- | --- |
| Exact cached claim | cached/legacy | cached/warrant |
| Evidence-bounded rewrite | bounded_rewrite/legacy | bounded_rewrite/warrant |

The paired 2×2 contrast in automatic full-support rate is an **apparent** interaction, not an improvement in truth. A writer could raise apparent precision simply by deleting substantive content or abstaining. Therefore the development comparison also reports output status, claims per output, independently reviewed support labels, false-full-support, judge error, and **retention of all evidence-supported material content in the sampled source assertion**. A partial source claim can still contain supported material; a disclaimer that omits a measured field/value/comparison fails retention. An empty output gets zero retention and undefined claim precision, not a perfect score. This does not measure recall of the entire original diagnosis output.

For each cell, case values are averaged within source output, then within family, then across families; raw claim-level confusion and per-class F1 are diagnostics. Invalid judge responses stay in the gold-reference denominator as `invalid_response` and count as errors. A support-overgrading event is a full-support prediction for a non-full reference, or a partial-support prediction for an unsupported/contradicted reference. `unsupported` and `contradicted` are **not** ranked against each other. Source-force false-full-support is reported separately for source claims typed `cause_assertion` or `recommended_action`, with all non-full reference claims in those source cases as its denominator. The 160 probability and 40 enriched components remain separate; no unweighted pooled population claim or inferential confidence interval is made from this adaptive development sample.

## Reference and execution boundary

The exact cached claim and evidence may reuse its locked human-final label. Any changed text or claim type requires a new development judgment; a row-position transfer is invalid. The private review packet contains only source text, generated text, visible evidence, and the material-content criterion—no writer name, automatic vote, human label, arm, or family. The reviewer fills labels and binary content retention **before** a coordinator compares against the exact-text seed and compiles the reference file. This is an internal development review, not a new independent human validation. Selection of a promising cell requires complete reference and retention review. Invalid judge output remains a measured error; it does not trigger a retry or erase its case. The analysis deliberately does not auto-select a winner.

Offline preparation writes only to a private directory outside Git. It pins the completed human-audit packet, sample map, human-final seed, code, prompts, sample census, model, destination, timeout, retry rule, and a conservative call/cost ceiling. The paid path is not run by preparation. If separately authorized, execution first sends one synthetic claim through the same writer/judge wire contract; an invalid or empty synthetic rewrite stops before the real cohort. The cohort has at most four concurrent cases, zero SDK retries, one immutable result per case, and a completion receipt. The original study artifacts are read-only. A caller exception can still represent a charged provider attempt, so unknown usage is reserved at the maximum rather than treated as free. `store=false` does not itself remove the provider's default abuse-monitoring retention; the exact private payload needs separate action-time approval under the [official API data controls](https://developers.openai.com/api/docs/guides/your-data). Current list rates and snapshot availability must be rechecked before purchase; the plan records the rate assumption used for its ceiling.

The four cells share source claims, evidence, provider family, and often source outputs. They are correlated comparisons. Prompt change is the intended judge intervention; format failures, latency and cost are part of the result. A development winner, if any, needs a fresh blinded set of new claims/families before a generalization or paper-level superiority claim.

The design follows the distinction between atomic factual precision and substantive coverage in [FActScore](https://aclanthology.org/2023.emnlp-main.741/), and the general factorial principle of isolating component effects in [NIST's factorial-design guidance](https://www.itl.nist.gov/div898/handbook/pri/section3/pri333.htm). Recent work on [construct validity of LLM judges](https://arxiv.org/abs/2608.24419) reinforces why the judge must respond to the changed claim rather than a stale label. The pinned snapshot, supported structured output, endpoint, and list token prices are specified in the [official OpenAI GPT-4.1 documentation](https://developers.openai.com/api/docs/models/gpt-4.1).

No paid API call, rewritten real claim, development reviewer label, or scientific result is claimed merely because the offline code and synthetic tests pass.

## Operator flow

The `scripts/warrant_development.py` entrypoint implements four actions: `prepare`, `execute`, `finalize-references` and `analyze`. Each accepts the private `--directory` (or `--memory-root`). `execute` additionally requires the displayed `--confirm-plan-sha256`; it verifies the code and inputs, runs the synthetic contract smoke, then processes the complete cohort with progress after each completed case. A failed smoke stops before the cohort. An existing lease prevents accidental repeat billing.

At completion, the directory contains immutable per-case results, an execution receipt, a reference template and a blind reference-review packet. Reviewers edit only the label and retention fields of a copy of the review packet. `finalize-references --review PATH` validates that copy against the original claims/evidence and compiles exact-output references. `analyze --references PATH` computes the reviewed comparison. Until the review is complete, analysis explicitly reports that candidate selection lacks complete references.

For 200 cases, the maximum is 1,809 calls: one rewrite plus two judgments of the cached claim and up to six judgments of three rewritten claims per case, plus up to nine synthetic calls. There are no automatic retries. The conservative reservation is $44.457984 at $2/million input and $8/million output tokens; this is a ceiling estimate, not a predicted charge. The actual invoice can differ from the estimate. Results and reference packets remain outside Git.
