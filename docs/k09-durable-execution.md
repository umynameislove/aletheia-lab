# K09 durable execution profile

The managed API and managed worker use `PostgresJobs(execution=True)`. Operator migration installs the current persistence profile before either process becomes ready. `execution=False` remains an explicit compatibility profile for historical local fixtures; its older immediate-cancel/retry behavior is not evidence for this profile. The frozen Job and JobReceipt schemas are unchanged. The additive capability is `jobs.execution_v1`.

Admission commits the job, stable request hash/key and audit before returning 202. Repeating the same key returns the original receipt even when the queue is now full. A different request with the same key is a conflict. Current authority, source/project scope and business revision are checked again at publication. A returned 503 does not authorize a new key; reconcile using the original key and job ID.

## Defaults and bounded policy

`QueuePolicy` is trusted constructor configuration: at most 32 queued/running/cancel-requested jobs per workspace, 8 per operation; at most 2 live execution leases per workspace and 1 per operation. A full queue rejects admission with 503 and creates no job/audit. Persisted workspace/class turns rotate eligible claimants; a hot class cannot consume every slot available to its workspace. Worker process slots remain separately configured. These are bounded local policy defaults, not a 50k-user or latency qualification.

Every job retains its original 15-minute database deadline and maximum three consumed attempts. Managed workers claim a 120-second lease and renew at most every five seconds, always capped by the original deadline. A cryptographic lease digest fences each attempt; a new claim increments the persisted epoch. Old workers cannot heartbeat or publish after takeover. Only a real claim or renewal advances the attempt heartbeat timestamp; cancellation and terminal writes preserve it. A new claim clears the preceding failure classification, so a successful retry does not retain a stale failure kind. Startup/poll reconciliation sweeps at most 64 due jobs per slot at a time. A stopped service performs no background work; its durable pending jobs are reconciled on the next worker/status access.

Timeouts and worker busy/timeout failures retry the same job after a persisted 2/4-second backoff while budget remains. Invalid mappings/inputs and unexpected permanent computation failures do not retry indefinitely. After three attempts the job is failed; a passed deadline is expired. Manual retry creates one linked successor, retaining the original deadline and consumed attempts. The same retry key replays its receipt; a second key cannot fan out a terminal parent into more retry chains. `retryable` is derived from remaining database-clock budget, authority and whether a successor already exists.

Queued cancellation is immediately terminal. Running cancellation first returns `cancel_requested`, with no terminal timestamp, and fences publication. The worker cancels computation, waits for the isolated child to be reaped, then acknowledges `cancelled`. If its owner is lost, an expired lease/deadline can close the request while the database fence still rejects late publication. A success that committed first remains succeeded. Scheduler stop drains active work; forced interruption leaves a recoverable lease rather than claiming completion.

Large immutable snapshot validation, hashing and serialization run outside database checkouts on cancellation-drained blocking tasks. Preparation and the single first-capture reconciliation have a separate finite 30-second budget; each database publication transaction retains its five-second budget. Cancelling a caller waits for its blocking task/isolated child to finish cleanup before releasing the job slot.

Analysis admission validates the exact workspace/project/snapshot route and current source permissions using metadata, then rechecks authority in queue admission. It does not read a large canonical object before the ACK. Full canonical bytes, hashes and deterministic analyzer checks remain worker/publication boundaries: a durably accepted job may correctly fail if its canonical parent is corrupt. A 202 promises durable acceptance, not a successful result.

## Reconnect and history

Poll the original status URL/ID after reconnect; do not create a replacement job to recover a lost response. Progress remains `null` when no measured fraction exists. GET/HEAD `/v1/workspaces/{workspace_id}/jobs/{job_id}/attempts` returns `JobAttemptPage`, with at most three ordered epochs, start/heartbeat/lease/finish times, outcome and bounded failure classification. It never returns the credential, lease digest or request payload. Current session, membership and parent authority are required on every read.

Finished attempt rows and terminal job states cannot be reopened. The commit audit records admission, retry by epoch, publication, cancellation and expiry in the same transaction as the corresponding durable effect. Migrated old jobs expose only the current known epoch; unknown start/heartbeat timestamps are null. A missing legacy terminal time uses the migration observation time, not a claimed historical execution finish. Missing `analysis_model` on an old accepted analysis job remains the original observation algorithm. New managed admissions pin their analysis model in the durable request before hashing, preventing restart/retry from changing scientific behavior. An unchanged implicit client request/key replays its admitted receipt across old/new server defaults; an explicit model or question change still conflicts.

## Local verification scope

`tests/integration/test_k09_execution_postgres.py` uses UUID-owned schemas on opt-in native PostgreSQL. It covers separate-process loss and real lease takeover, stale-worker publication, actual canonical effect/audit counts and lost-response replay, cancellation in both publication orders, three attempts with real database backoff, manual retry/deadline invariants, tenant/class admission and claim races, unprivileged API/worker grants and immutable history. A controlled real subprocess proves heartbeat and cancel → reap → terminal acknowledgement; it does not claim that every scientific algorithm was running in that controlled child.

`tests/unit/test_k09_execution.py` covers repeated cancellation during child cleanup, bounded failure classification, strict attempt DTOs and HTTP scope checks, and the managed worker's actual inferred virtual-environment interpreter. Existing local API SIGTERM and worker drain witnesses remain separate receipts. No Docker, real IdP, Windows execution, distributed database failover, Quân browser receiving or remote CI acceptance is implied by these local tests.
