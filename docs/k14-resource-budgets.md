# K14 — process resources and backpressure

Run `python scripts/k14_resource_plan.py --config <runtime.toml> --api-replicas N --worker-replicas M` with the actual fleet counts. This reads configuration without resolving database credentials. A nonzero exit means the declared fleet exceeds the declared PostgreSQL connection budget or input is invalid.

The connection bound is `API replicas × API processes × API pool + worker replicas × worker processes × worker pool + admin reserve`. The reserve is added once for the declared database, not once per replica. Every deployment must include all API and worker replicas. Default one API process/pool 8 and one worker process/pool 2 plus admin reserve 2 require 12 connections from the configured budget of 16. Three default API replicas already exceed that budget.

Each process has two actual blocking calls and at most 32 FIFO asynchronous waiters **before** the executor. Waiting cancellation removes the waiter without starting the call. Once a thread starts, caller cancellation drains it before returning its permit; repeated cancellation cannot make another thread reuse that permit early. The queue is shared across event loops in the same process, including Windows bridges. Shutdown-only thread joins remain outside this gate so a shutdown can release an occupied permit.

Source part hashes, source verification, ZIP inspection, filesystem writes/reads, and assembly hashes/copies run off the event loop. Large assembly releases its database connection before hashing/copying. Before fetching any staged payload, source completion reserves twice the manifest size from a process-local 400 MiB logical-byte budget: one 200 MiB completion, or a bounded sum of smaller completions. Overload starts no assembly and returns 503. Committed `ready` replay still works under full materialization pressure. Modern completion cancellation retains this reservation until its actual inspector finishes. The bound measures retained part and assembled bytes; driver buffers, Python allocator overhead, incoming request buffers and inspection workspace also consume RSS. It is not a 400 MiB RSS promise.

Export creation has one active operation and at most four FIFO waiters per process, before any private view or render input is loaded. A cheap current export/source/project scope check and authorized existing-receipt lookup precede admission. Waiters hold scalar intent only, with no database connection or view bytes. The active operation rechecks current authority and keyed receipt, loads/serializes one view, uses the unchanged single report worker and publishes under fresh authorization. Already committed matching-key replay remains available while the FIFO is full; expiry/conflict/current denial still apply. A sixth new authorized export receives 503/Retry-After, while HTTP/action deadlines continue to include queue wait. Waiting cancellation starts no render; running cancellation retains admission until the actual report child has been reaped, including repeated cancellation and the Windows bridge.

This export queue addresses a concrete brief-burst failure: the preserved 100-VU open run logged 18 report-render errors taking zero milliseconds, corresponding to immediate busy rejection from the occupied one-slot report worker. It does not add workers, extend HTTP/worker/journey deadlines, alter profile weights or turn the older 503 outcomes into success. Native tests verify five queued/active exports, full-queue durable receipt replay, byte hashes, current source/session/tombstone denial after waiting, and real child cleanup. The separate final 100-principal debug calibration retained the same offered business workload and completed 486/486 positive actions plus 14 expected denials, including 50 fully verified exports. That passing subset does not qualify the primary campaign.

The ASGI application admits at most the configured concurrency: normally 63 regular requests plus one health probe at the default 64. The extra health lane is reserved inside that total. It never queues extra request tasks or reads a rejected request body. With concurrency 1 health shares the sole slot. An ingress server's independent open-connection limit can reject before this application; configure/test reverse-proxy and keep-alive limits on the actual topology. This local lane does not override Uvicorn admission.

Unavailable capacity yields 429 for bounded workspace job polling or 503 for process/worker resources, with `Retry-After` and `Cache-Control: no-store`. Clients keep their original intent and idempotency key, add jitter, and retry when appropriate. A browser disconnect never cancels a durable accepted job. Existing queue deadlines, attempts, workspace/class limits and transaction fences remain authoritative. GC uses immediate blocking admission while holding database fences, so it defers instead of waiting for a thread under a connection lock.

Observe `blocking_active`, `blocking_waiting`, `http_inflight`, `job_poll_inflight`, rejection counters, pool wait, event-loop lag, RSS/FD/CPU and queue delay on every process. Telemetry records actual blocking execution separately from queue wait. Add fleet values by role/process; never reinterpret a process gauge as a cluster total.

`measured_mean_demand` computes mean in-flight demand (`arrival/s × mean wall seconds`) and mean CPU demand (`arrival/s × mean CPU seconds`). Use completed sample counts and measured costs. This arithmetic excludes tails, waiting/failed work, database/I/O bottlenecks and a saturated generator. Normal traffic returning 429/503 counts as failure in the normal-capacity gate. A bounded burst response is only an overload-safety result.

Local correctness and measured native probes are recorded in the K14 evidence directory. A normal 50k-user run, multiple replicas, ingress FD/keep-alive measurements and noisy-tenant fairness on the declared deployment remain deployment acceptance gates; these are not implied by unit tests, a smaller local probe or this resource plan.

The follow-up `test_k14_process_envelope_postgres.py` runs an actual TLS API and two-slot upload worker against a dedicated native PostgreSQL cluster. Two ten-job bursts each contain eight noisy-workspace and two background-workspace preview jobs. Each intent is submitted three times concurrently with the same key. All 60 HTTP admissions resolve to exactly 20 admitted/completed jobs, with one successful attempt per job and all 20 output source hashes verified. Actual attempt intervals enforce two running jobs globally and one preview per workspace; each workspace appears among the first two claims, and the background workspace completes work before the noisy queue exhausts. The worker restarts gracefully after each fully settled burst; this is controlled burst/startup coverage, not a continuous soak.

The six unique source ZIPs contain 1,000/10,000/100,000 real rows, with observed sizes about 41/406/4,083 kB. Native result dimensions remain 2/16/64 claims and 6/34/130 graph nodes, so only the source-row axis matches the primary fixture. Six first reads after a fresh API process are distinguished from six repeated reads. PostgreSQL and OS caches are uncontrolled; this is application-cold/warm coverage. The passing local run served 216 background reads and 216 readiness probes, all 200: observed read p95 54.72 ms and health p95 6.26 ms, with only 216 observations per endpoint and no precise p99 claim.

The same window samples kernel CPU, lifetime peak RSS, open FDs and telemetry every 100 ms, plus live API/worker/PG process trees and actual database connections. The reference run observed API peak RSS about 110 MiB and 17 FDs, worker-process peaks about 124/118 MiB and 14 FDs, single reaped-child peaks about 130/127 MiB, and API/worker pool peaks 4/2. Quiet-job first completion occurred about 404/375 ms after the first claim. Live-tree sampling can miss short children and RSS sums double-count shared pages. Kernel reaped-child CPU includes completed children, while its RSS maximum is for one child. These mixed-load observations do not attribute CPU to individual operations, impose a deployment RSS/FD ceiling, or measure NIC/ingress/multiple-replica headroom. The deployment resource envelope and full mixed-workload fairness remain open.
